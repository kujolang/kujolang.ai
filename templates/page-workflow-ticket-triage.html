Support ticket triage

Classify a ticket and draft a reply for a person to review.

Offline demo + live modeDownload application ↓

What you will build

A customer reports a duplicate charge. The output includes a billing category, invoice ID and unsent reply.

Output artifact

triage.json

Saved locally for you to inspect and use.

main.kujo

Source ↓
from common import load, save, config, request, require_result

let input := load("input.json")
let result := request(config(), "Triage the support ticket. Extract its invoice ID and draft a reply for human review. Do not promise refunds or claim actions have been taken.", input, "responses.json", load("schema.json"))
let data := require_result(result)
assert(contains(input["message"], data["invoice"]), "Invoice must occur in the ticket")
save("triage.json", {"ticket_id": input["id"], "classification": data, "attempts": result["attempts"], "status": "awaiting_human_review", "sent": false})
print("Saved triage.json. No reply was sent.")

Run it locally

Start offline.

Install Kujo, download the application, then run these commands from your download directory.

unzip ticket-triage.zip -d ticket-triage
cd ticket-triage
kujo run main.kujo

The ZIP includes main.kujo, common.kujo, input, schema, response fixtures and README.md. Run inside its extracted directory. No key or network request is needed in offline mode.

Read the shared request policy ↗

Offline responses are authored test fixtures. They demonstrate control flow, not live model quality.

How it works

  1. Read the ticket and request a constrained category and priority.
  2. Retry an invalid response within a two-request limit.
  3. Check that the extracted invoice occurs in the ticket; save an unsent draft.

Try a failure. Then recover.

The first authored response is invalid JSON. The second is valid, so the report records two attempts. Replace both with invalid text to reach failure.json; restore the responses to recover.

Use a fresh extraction to restore the original fixtures. A failed run does not make an older output file current; check the exit status before consuming results.

Connect a live provider

Live mode sends your input to the configured provider and may cost money. Choose an OpenAI-compatible endpoint and model you can access, then set credentials in your environment. The example sends at most 1,024 output tokens per request and normally allows two attempts. The batch and regression examples apply that limit per item.

export KUJO_WORKFLOW_MODE=live
export KUJO_AI_ENDPOINT=https://your-provider.example/v1/chat/completions
export KUJO_AI_MODEL=your-model
# Set KUJO_AI_KEY securely in your environment.
kujo run main.kujo

Live transport was tested against a controlled local HTTP server, including failure and timeout cases. No paid provider call or claim about model quality is part of this demo.

Make it yours

Replace input.json with a ticket from your own queue and adjust schema.json categories. Review the draft and billing facts before sending anything. The application has no sending integration.

Know the boundary

Schema validation cannot guarantee that a reply is appropriate or that its promises are true. The output remains awaiting_human_review.

Source and verification

Checked and executed with Kujo 1.9.0. Offline fixtures and local HTTP provider tests cover success, rejection and recovery.
