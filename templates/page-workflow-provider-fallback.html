Provider fallback workflow

Try a second provider within a bounded request budget.

The primary response fails validation. The backup returns a usable classification and the report records both attempts.

Source ↓
from common import load, save, config, request, require_result

let input := load("input.json")
mut trace := []
mut budget := 2
for provider in input["providers"] {
    if budget > 0 {
        mut cfg := config()
        cfg["max_attempts"] := 1
        cfg["provider"] := provider
        let result := request(cfg, "Classify this support message as billing, account or technical.", {"text": input["text"]}, "responses-" + provider["id"] + ".json", load("schema.json"))
        budget = budget - 1
        trace = push(trace, {"provider": provider["id"], "ok": result["ok"], "errors": result["errors"]})
        if result["ok"] {
            save("routing.json", {"selected": provider["id"], "result": result["data"], "trace": trace, "requests_remaining": budget})
            print("Saved routing.json using " + provider["id"] + ".")
            exit(0)
        }
    }
}
save("routing.json", {"selected": null, "trace": trace, "requests_remaining": budget})
print("No provider returned a valid result within the two-request budget.")
exit(2)

Run it locally

Start offline.

Install Kujo, download the application, then run these commands from your download directory.

unzip provider-fallback.zip -d provider-fallback
cd provider-fallback
kujo run main.kujo

The ZIP includes main.kujo, common.kujo, input, schema, response fixtures and README.md. Run inside its extracted directory. No key or network request is needed in offline mode.

Read the shared request policy ↗

Offline responses are authored test fixtures. They demonstrate control flow, not live model quality.

How it works

  1. Try the configured primary once with a two-second timeout.
  2. Treat transport errors and schema failures as unsuccessful attempts.
  3. Try the backup once, then stop and save the routing trace.

Try a failure. Then recover.

The primary fixture is invalid by design. Make the backup invalid too to exhaust the two-request budget and exit 2. Restore the backup fixture to recover. Tests also exercise a real local HTTP timeout.

Use a fresh extraction to restore the original fixtures. A failed run does not make an older output file current; check the exit status before consuming results.

Connect a live provider

Live mode sends your input to the configured provider and may cost money. Choose an OpenAI-compatible endpoint and model you can access, then set credentials in your environment. The example sends at most 1,024 output tokens per request and normally allows two attempts. The batch and regression examples apply that limit per item.

export KUJO_WORKFLOW_MODE=live
export KUJO_PRIMARY_ENDPOINT=https://your-primary.example/v1/chat/completions
export KUJO_PRIMARY_MODEL=your-primary-model
export KUJO_BACKUP_ENDPOINT=https://your-backup.example/v1/chat/completions
export KUJO_BACKUP_MODEL=your-backup-model
# Set KUJO_PRIMARY_KEY and KUJO_BACKUP_KEY securely in your environment.
kujo run main.kujo

Live transport was tested against a controlled local HTTP server, including failure and timeout cases. No paid provider call or claim about model quality is part of this demo.

Make it yours

Configure primary and backup endpoint, model and key variables independently. Use providers that accept the OpenAI-compatible chat format. Tune timeout and output-token limits in common.kujo for your workload.

Know the boundary

The budget limits request count and per-request output tokens, not dollar spend. A timed-out provider may still complete and charge for a request. No unbounded retries or automatic provider discovery are performed.
