<section class="workflow-section"><h2>How it works</h2><ol class="workflow-steps"><li>Ask for complete before and after text for the allowed file.</li><li>Validate the path and original contents, then save a proposal and preview.</li><li>Require the printed proposal hash and unchanged source before applying.</li></ol></section>
<section class="workflow-section workflow-failure"><h2>Try a failure. Then recover.</h2><p>Run the printed apply command with a wrong hash, or edit draft.txt after preview. The application refuses to apply. Generate a new preview and review it before approving its new hash.</p><p>Use a fresh extraction to restore the original fixtures. A failed run does not make an older output file current; check the exit status before consuming results.</p></section>
<section class="workflow-section"><h2>Connect a live provider</h2><p>Live mode sends your input to the configured provider and may cost money. Choose an OpenAI-compatible endpoint and model you can access, then set credentials in your environment. The example sends at most 1,024 output tokens per request and normally allows two attempts. The batch and regression examples apply that limit per item.</p><div class="sample-code"><pre tabindex="0"><code>export KUJO_WORKFLOW_MODE=live
export KUJO_AI_ENDPOINT=https://your-provider.example/v1/chat/completions

<section class="workflow-section"><h2>Make it yours</h2><p>Start in the extracted bundle directory, which includes a disposable draft.txt. Adapt the allowed path and content checks deliberately. Never pass the model output to a shell. preview.diff is a human before/after display, not an apply-ready patch.</p><h3>Know the boundary</h3><p>Approval is a content check, not an operating-system sandbox. Use a trusted local directory with a regular draft.txt and no concurrent writers. For hostile workspaces, use filesystem isolation and race-resistant file operations.</p></section>
