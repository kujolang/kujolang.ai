Keep your language. Make the work inspectable.

Suppose an agent needs to add a customer API endpoint to a Python or TypeScript repository. Choose the tools you need for each stage. You configure their commands, environment and review rules; they do not connect automatically.

  1. Define scope: describe the endpoint, expected behavior and excluded changes. Spec can express a task contract.
  2. Retrieve context: inspect relevant routes and tests. Scout analyzes repositories; Scent creates bounded context packs.
  3. Execute: implement in your checkout or a separately configured Workcell environment. Isolation depends on the selected backend and policy.
  4. Evaluate: run the repository’s real tests. Eval and Lens can provide configured evaluation and browser checks.
  5. Inspect evidence: review the Git diff. PatchBrief summarizes changes; ChangeBucket measures their footprint.
  6. Assess readiness: ShipCheck evaluates declared release conditions. Deployment still belongs to the project’s authorized pipeline.

These tools also work with non-Kujo code. Install and configure each one separately.

Reproduce the local gate-and-evidence stage

Prerequisites: Git, Bash and the target project’s existing test command. Clone the Loop Engineering source beside a disposable test repository:

git clone https://github.com/kujolang/kujo-workflows.git
cd your-existing-project
../kujo-workflows/loop-engineering/scripts/init-repo-loop.sh

Inspect any existing .loop-engineering/ before initialization. Set the objective and real commands in .loop-engineering/loop.yml; the following is a minimal example for a project that already has a working npm test script:

objective: "Implement and verify the customer endpoint within the agreed scope"
max_iterations: 2
max_no_progress: 1
max_consecutive_failures: 2
eval_gates:
  - id: project_tests
    command: "npm test"
    required: true
  - id: diff_check
    command: "git diff --check"
    required: true
commit:
  enabled: false
  push: false

After implementing the endpoint and its tests:

../kujo-workflows/loop-engineering/scripts/run-workflow.sh --config .loop-engineering/loop.yml

Inspect .loop-engineering/SUMMARY.md, ledger.tsv and iterations/001/. Each iteration records context, action, diff, evaluation logs and verdict. The Bash runner gates and records work; it does not implement an endpoint or invoke an AI agent on its own. Inspect the verdict file: the process exit alone does not establish that gates passed. A passing test command only proves the assertions it actually ran.

This website uses the same runner. Its committed workflow state provides a concrete example of scoped changes and recorded checks.
