Measure the workload you actually need

Kujo runs on a bytecode VM by default. A compatibility interpreter is a different execution path. Neither should be confused with native compiled output or with JIT steady-state measurements from another runtime.

This page makes no claim that Kujo is faster than another language. Cross-language workloads are unmeasured here. Existing comparison pages describe evidence and adoption tradeoffs rather than a universal speed ranking.

Reproduce the small-script measurement

The site includes a measurement script and a machine-readable receipt. Run it from the website source after installing Kujo 1.9.0:

python3 scripts/measure-language.py

The workload is the pinned functions example, summing three values and printing the result. The script records operating system, architecture, CPU, runtime version, source hash, command, ten process runs and median wall time. It checks output on every run. This is a process startup plus script execution measurement, including CLI and output overhead, not a steady-state VM benchmark. It cannot support conclusions about application throughput, memory use, parallelism or other languages.

All ten launches are included; no warmup runs were discarded. Background load and the host machine affect these numbers. Use the raw receipt to inspect variation rather than treating the median as a guarantee.

For larger experiments, inspect Kujo benchmark sources and the runtime’s kujo bench --help. Record compiler flags, dependency versions, CPU, OS, warmup, sample count, input data and output equivalence. Separate startup, compilation and steady-state time. Publish raw results and uncertainty before drawing comparisons.
